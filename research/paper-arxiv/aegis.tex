\begin{abstract}
AI agents now execute tool calls---database queries, shell commands, payments, email---and most agent frameworks forward those calls to execution with nothing in between. Observability records what an agent did; it cannot stop it.

\system{} is an open-source control point between an agent's decision to call a tool and the tool running.\footnote{Open-source (MIT). Code, harnesses and corpus: \url{https://github.com/Justin0504/Aegis}.} Integration is two lines and covers 15 agent frameworks in Python, JavaScript and Go, plus an MCP proxy and a provider-compatible egress proxy. Each call is decided by layers ordered by what they may observe---pattern rules over the call string, a behavioural anomaly stack over the agent's own history, an \emph{instruction-provenance} check over which channel of the conversation authorised the call, and a declarative policy over all of their facts---and returns \texttt{allow}, \texttt{block}, or \texttt{pending}, which suspends the agent until a person or the alignment auditor decides. A refusal comes back where a tool result would, so a blocked agent explains itself and continues. Every decision is Ed25519-signed and hash-chained.

On AgentDojo, with a gpt-4o-mini agent, \system{} reduces attack success from 29.7\% to \textbf{1.4\%}, the lowest of the defenses compared, against 5.4\% for an LLM tool filter. The cost is holds: with no reviewer, clean-task utility falls from 69.1\% to 38.1\%; with the alignment auditor as first reviewer it is 56.7\% and 11 of 97 tasks reach a person. With a locally served qwen3:8b as agent and auditor on two suites, the shipped gateway with the auditor shown the agent's evidence lets 1 of 249 attacks run at 13 of 37 clean tasks against 19 undefended; we report the defects that run exposed and fixed. A check takes 0.44\,ms at the median, and one gateway process sustains about 2{,}300--3{,}000 checks per second. On tool calls live agents emitted under attack, content inspection is at chance and the provenance layer separates them, and we report where it does not: an injection that stays inside the tool the user already asked for. Running the shipping gateway under nineteen agent harnesses found and fixed twenty-six defects no unit test had caught, which we list. Numbers reported in this paper's first version are withdrawn; an appendix gives the audit.
\end{abstract}

\section{Introduction}
\label{sec:intro}

AI agents do not only generate text; they take actions.
ReAct~\cite{yao2023react} showed that LLMs can interleave reasoning with tool invocations, and modern frameworks such as LangChain~\cite{langchain2023}, CrewAI~\cite{crewai2024}, and LlamaIndex~\cite{llamaindex2024} have made tool-augmented agents widely accessible.
However, these capabilities create a direct path from model output to real-world side effects---a path that can be triggered by adversarial prompt injection~\cite{greshake2023not} or hallucinated reasoning.
In most current stacks, once the model emits a tool call, the framework forwards it to execution with no pre-execution control point.

Post-execution observability platforms such as Langfuse~\cite{langfuse2024} and Arize~\cite{arize2024} can record these events, but they cannot prevent side effects before they occur.
Existing defenses sit at two extremes: rule-based layers are fast ($<$1\,ms) but see only the call string, while LLM-judge layers can read the call against the user's task but add seconds of latency per call.

\system{} is that control point. It stands between an \emph{unmodified}
agent and its tools, decides each call before it runs with layers ordered
by \textbf{what they may observe}---the call string, the agent's history,
the conversation's trust channels, the stated task---and returns the
decision in-band, so a refusal reads to the agent like a tool error it can
recover from, and a hold suspends the turn until someone answers.

The question a deployment asks of such a system is not how a detector
scores single calls but what happens to its agents. On AgentDojo
(\S\ref{sec:agentdojo}), the benchmark the closest systems report against,
\system{} cuts attack success from 29.7\% to 1.4\%. It does so mostly
through the instruction-provenance layer, which asks which turn of the
conversation authorised a call rather than what the call contains, and
which costs under a millisecond and no model call
(\S\ref{sec:overhead}). Its cost is holds, and we report them as such:
the share of clean tasks that need a person, and how far the alignment
auditor, used as first reviewer, brings that down. We also report what
the layer cannot see (\S\ref{sec:scope}).

The paper is written for someone deciding whether to put this in front of
their agents. Section~\ref{sec:arch} describes the system; Section~\ref{sec:eval}
measures it end to end, in cost, and per call on attacks live agents
actually emitted; Section~\ref{sec:demo} walks through it on a real agent;
and Appendix~\ref{app:compat} runs the shipping gateway under nineteen
agent harnesses---the exercise that found most of the defects this
version fixes.

\medskip\noindent Our contributions are:
\begin{enumerate}[nolistsep,leftmargin=*]
\item A \textbf{pre-execution control point} for unmodified agents: two
      lines in 15 frameworks across Python, JavaScript and Go, an MCP
      proxy and an egress proxy, returning allow, block or a hold before
      any side effect, in-band, with every decision signed and chained.
\item \textbf{Instruction provenance} as a decision layer: a per-session
      ledger of the conversation's trust channels and a measure of which
      channel explains a call, enforced by a shipped policy pack, and its
      limit---an injection that stays inside the tool the user asked for.
\item An \textbf{end-to-end evaluation} on AgentDojo against AgentDojo's
      own defenses, with utility reported as holds and the tasks that
      need a person, and an overhead measurement under concurrent load.
\item A \textbf{per-call corpus of agent-emitted attacks} built by
      compromising a live agent, with a matched control, on which content
      inspection is at chance; and the audit that withdraws this paper's
      first-version numbers (Appendix~\ref{sec:withdrawn}).
\item A \textbf{compatibility matrix} of nineteen harnesses run against
      the shipping gateway, and the twenty-six defects it found.
\end{enumerate}

\section{System Architecture}
\label{sec:arch}

\system is organised around one commitment: every tool call an agent
emits passes through a point at which it can be decided on, and that
decision is returned to the agent in-band, before any side effect occurs.
This section follows a single call through the system (Figure~\ref{fig:architecture}): how it is
captured, what each layer may observe about it, how a policy turns those
observations into a decision, what happens when a person must be
involved, and how the whole episode is made auditable afterwards.

\subsection{Threat Model and Trust Boundary}
\label{sec:threat}

The LLM is an \emph{untrusted component}. It may emit a harmful tool
call because its context was poisoned by indirect prompt
injection~\cite{greshake2023not}, because it hallucinated an action, or
because it was jailbroken. Nothing the model writes is treated as an
authority. The trust boundary runs between two channels of the agent's
context: what the \emph{principal} typed, and everything that entered
from outside---tool returns, retrieved documents, fetched pages, email
bodies. A tool return is untrusted even when the tool is one the
operator wrote and the server is one the operator runs, because the
content it carries may not be theirs. The SDK and Gateway are trusted
enforcement components; \system does not defend against an agent that
bypasses the SDK entirely, and it does not defend the gateway host.

\subsection{Interposition: Three Ways In, One Gateway}
\label{sec:sdk}

\paragraph{SDK instrumentation.}
The primary path patches the model client at import time:

\begin{lstlisting}[language=Python, basicstyle=\scriptsize\ttfamily]
import agentguard
agentguard.auto()  # patches every detected SDK in-process
\end{lstlisting}

\noindent \texttt{auto()} wraps the request method of each model client
it finds---Anthropic and OpenAI (sync and async), LangChain and LangGraph
(through \texttt{langchain\_core} tools), CrewAI, AutoGen, Gemini, Bedrock,
Mistral, LiteLLM, LlamaIndex, Pydantic~AI, smolagents~\cite{smolagents2024},
the OpenAI Agents SDK (at the tool), the Claude Agent SDK, and a generic HTTP-tool shim; fifteen targets---and
exposes two hooks. On the \emph{response}
side it extracts every \texttt{tool\_use} block, sends
\texttt{(tool\_name, arguments, session\_id)} to the Gateway, and
suspends dispatch until a decision returns. On the \emph{request} side,
which is new in this version, it reads the outgoing \texttt{messages}
array and classifies each span by trust channel before the model is
called (\S\ref{sec:provenance}), into one ledger per process unless the
host names its sessions, so the two lines stay two lines. The agent's code, prompts and tool
definitions are untouched. Where the decision is \emph{enforced} is a
switch, \texttt{enforce\_at}: at the response, the SDK raises out of the
model call before dispatch; at the tool, the model-level patch only
observes and a tool-level patch on the framework's own dispatch method
(LangGraph, CrewAI, AutoGen, LlamaIndex, smolagents, Pydantic~AI, the
OpenAI Agents SDK) returns the refusal as the tool's result, so the model
sees it in the slot a result would occupy. A stack with no such method
to patch---a hand-written loop, LiteLLM, the Google GenAI client---gets
the same behaviour from one line that wraps its dispatcher,
\texttt{agentguard.guarded(execute\_tool)}. The JavaScript SDK patches
Anthropic, OpenAI and LangChain and ships the same \texttt{enforceAt}
switch and \texttt{guarded} helper; the Go SDK is an explicit
\texttt{Wrap(tool, args, fn)} that checks, holds, runs and traces.

\paragraph{MCP proxy.}
For agents that reach tools over the Model Context Protocol, a stdio or
HTTP proxy sits between the host and the MCP server, forwards
\texttt{tools/call} requests through schema validation, L1 and the policy
DSL in-process, with the kill switch, and rewrites refused calls into tool
errors. Nothing in the host changes.

\paragraph{Egress proxy.}
For stacks where neither is available, the gateway accepts the model
provider's own API surface at \texttt{/api/v1/proxy}, so pointing
\texttt{OPENAI\_BASE\_URL} or its equivalent at \system is a complete
integration. The proxy decides inline: it runs the detector chain of
\S\ref{sec:pipeline} and the tenant's policy over every tool call in the
model's response, and because an inline HTTP response cannot be held
for a person, a \texttt{pending} decision is treated as \texttt{block} and
the audit record says so. A policy is written once and applies on all
three paths; the behavioural and provenance layers below run on the SDK
path, which reaches the full \texttt{/api/v1/check} pipeline.

\subsection{The Decision Pipeline}
\label{sec:pipeline}

A call that reaches \texttt{/api/v1/check} is decided by layers ordered
by \emph{what each may observe}, not only by cost. The ordering matters
because the measurement in \S\ref{sec:eval} turns on it: layers that see
only the call string are blind to a class of attack that layers which
see the conversation can resolve.

\paragraph{Identity and scope.}
Before any content is read, the call is attributed. The agent is looked
up in the registry (and created on first sight), an agent the operator
has suspended or the kill switch has revoked is refused, and an agent
with a \emph{declared tool scope} may only call the tools it declared:
a call to an undeclared tool is blocked as \texttt{unattested-tool}
before extraction. Scope is opt-in per agent, so an unscoped agent is not
blocked by a check it never asked for.

\paragraph{Extraction.}
Arguments are walked recursively (depth limit 32, 10{,}000-string cap)
and every string-bearing leaf is collected. This is what L1 sees.

\paragraph{L1: pattern rules ($<$1\,ms).}
28 risk patterns in 11 types (Table~\ref{tab:patterns}) are matched
against the extracted strings. A hit is an immediate block with a named
reason. L1 is the right tool for a \emph{payload} that is itself
hostile---a SQL statement with a stacked \texttt{DROP}, a path with
\texttt{../}, a shell string with \texttt{\$\{IFS\}}---and, as
\S\ref{sec:eval} shows, nearly inert against a call whose arguments are
ordinary.

\paragraph{L2: behavioural anomaly (in-process).}
Rather than a second look at the call string, L2 scores the call against
the agent's own history. A 16-dimensional behaviour vector---tool novelty,
frequency and recency; argument drift (Jaccard distance, length $z$-score,
key-count ratio); hour and interval deviation; burst ratio; sequence
surprise under a PPM-C model and bigram unlikeliness; cost $z$-score; risk
ordinal and high-risk rate---is scored by an Isolation
Forest~\cite{zhao2019pyod}, half-space trees and Mahalanobis distance,
calibrated into conformal $p$-values, with ADWIN~\cite{bifet2007adwin}
flagging drift so thresholds adapt rather than decay. A new agent is
cold-started from its tenant's aggregate baseline, and operator
approve/reject feedback is folded back into the scorer. L2 can escalate
or block an otherwise-allowed call and never relaxes one. It catches an
agent behaving unlike itself; it does not catch a single ordinary-looking
call, and \S\ref{sec:eval} measures that limit directly: on the rebuilt
corpus no surface feature of the call (Table~\ref{tab:features}) exceeds
AUC 0.585, because a successful injection does not make the call look
unusual.

\paragraph{Detector chain (proxy path).}
On the egress proxy the same facts are produced by a registry of
pluggable detectors keyed to an ATT\&CK-style agent threat ontology:
indirect prompt injection, data exfiltration, sensitive-context
exfiltration by taint tracking (the agent read a secret, then calls
outward), memory poisoning (instruction-shaped writes to scratchpads and
vector stores), reconnaissance, lateral movement, tool scope against an
agent's declared tool list, budget, cross-agent correlation and PII, with
the L1 classifier and the L2 stack wrapped as detectors of the same
interface. Operators register their own, and a coverage map reports
which ontology techniques the deployed set actually covers.

\paragraph{L$_\mathrm{p}$: instruction provenance ($<$1\,ms).}
\label{sec:provenance}
This layer asks a different question: not what the call contains but
\emph{which turn authorised it}. The Gateway keeps a per-session
\emph{context ledger}---a bounded record (64 events, 256\,KB) of every
span that entered the agent's context, tagged \texttt{user},
\texttt{untrusted} or \texttt{model}---populated by the SDK's
request-side hook. Four grounded features are computed from the ledger
and the call: \texttt{user\_licence} and \texttt{untrusted\_licence},
the fraction of the call's vocabulary (tool name split on case, argument
keys, argument values) that each channel accounts for;
\texttt{authority\_margin}, their difference; and
\texttt{tool\_named\_in\_untrusted}, whether untrusted text names the
tool being called and the principal does not. The licence measure is
asymmetric by design---it scores how much of the \emph{call} a channel
explains, not how similar two texts are---which is what makes the
obvious evasion (copying the user's request into the injection) inert
(\S\ref{sec:eval}). The result is a verdict in
\{\texttt{user}, \texttt{untrusted}, \texttt{unclear}, \texttt{unknown}\}
(Figure~\ref{fig:provenance}).
\texttt{unknown} is reported, never inferred: a session with no reported
user turn yields it, and every provenance rule in the shipped policy pack
requires a decided verdict, so an un-instrumented deployment sees no
behaviour change rather than a wall of false blocks. Ledgers are
namespaced by tenant; without that, an attacker who guessed a session id
could write a \texttt{user} event into another tenant's session and
launder an injected instruction into an authority.

\paragraph{L3: alignment auditor (1--2\,s).}
A frontier model receives the tool name, arguments and the user's stated
task and returns whether the call serves that task, with a rationale. In
the shipping gateway this is not an inline stage of the check: the SDK
may call the auditor (\texttt{/api/v1/alignment/check}) before the check
and attach its verdict, which the policy can match on
(\texttt{alignment.score}); and a trace judge scores recorded traces after
the fact. The judge of \S\ref{sec:eval} is the evaluation harness's own,
run as a detector over the corpus; it makes the same comparison, and it
is the only configuration meaningfully above chance on real injected calls
before L$_\mathrm{p}$ existed. Its cost is roughly $1600\times$ the rules
path.

\paragraph{Policy.}
\begin{sloppypar}
The layers emit facts; a declarative policy turns facts into a decision.
Policies are written in a small DSL over dotted field paths---
\texttt{tool.name}, \texttt{classifier.\allowbreak category}, \texttt{anomaly.score}, \texttt{alignment.score},
\texttt{provenance.\allowbreak authorised\_by}---\allowbreak with \texttt{all}, \texttt{any} and
\texttt{not} composition, and comparators including regular expressions.
The DSL is \emph{fail-safe}: a rule can tighten a decision (allow $\to$
pending $\to$ block) and can never relax a block imposed by schema
validation or anomaly detection to allow. Rules are compiled once per
tenant and evaluated in constant time per call. Eight packs ship
ready-made---GLBA, PCI~DSS, SOX, DORA, HIPAA, FedRAMP, a fintech
agent-payments pack, and the instruction-provenance pack of
\S\ref{sec:eval}---each carrying a citation to the clause it addresses so
an auditor can cross-check. A natural-language compiler drafts DSL from
prose for operators who do not want to write it by hand; the compiled
rule, not the prose, is what runs.
\end{sloppypar}

\paragraph{Decision.}
The call resolves to one of three outcomes, each with a distinct return
path. \texttt{allow}: the tool runs and its result returns normally.
\texttt{block}: the tool never runs, and a structured refusal is
returned \emph{in the slot a tool result would have occupied}---which is
why a blocked agent explains itself and continues the conversation
rather than failing (Figure~\ref{fig:demo}). \texttt{pending}: the turn
suspends until a person decides.

\subsection{Audit and Integrity}
\label{sec:audit}

\begin{figure}[t]
    \centering
    \includegraphics[width=\columnwidth]{images/audit_chain.pdf}
    \vspace{-0.15in}
    \caption{Each trace is signed with the agent's Ed25519 key and commits
    to its predecessor's hash. Editing one field of record $t$ fails
    verification for $t$ and everything after it; attendees are invited to
    do exactly this to an exported log.}
    \vspace{-0.15in}
    \label{fig:audit}
\end{figure}

Agents carry an identity card---an EdDSA-signed JWT minted by the gateway
and bound to the agent's registry status---which the proxy path verifies.
Every decision, with the facts that produced it, becomes a trace: the
SDK carries the gateway's verdict into the trace record it writes for
the call (\texttt{safety\_validation}, \texttt{approval\_status}), so a
blocked call, a held call and the person's answer to it are in the same
chain as the calls that ran, and the gateway records the same decision
in its violations table. Traces
are signed with a per-agent Ed25519 key~\cite{bernstein2012eddsa} and
linked into a SHA-256 hash chain in which each record commits to its
predecessor; modifying or deleting any entry breaks the chain for every
record after it. The chain belongs to the agent, not to a process: before
its first trace, an SDK asks the gateway where the agent's chain ends and
continues from there, so a restarted agent extends one chain rather than
starting a second (a defect the compatibility matrix exposed, since every
row there runs in a fresh process). Chain heads are periodically folded into a Merkle tree
and the signed root is appended to a transparency log, which registered
external \emph{witnesses} can countersign---so an operator cannot
quietly rewrite their own history even with the gateway's key. Offline
verification recomputes the chain and roots from an exported log and
fails loudly on any discrepancy; the demonstration invites attendees to
edit one record and watch it fail (Figure~\ref{fig:audit}). Compliance evidence packs assemble
traces, policies and verification results into the artefacts an audit
expects (SOC~2 control evidence, EU AI Act Article 12 record-keeping).
Retention is a policy too: per-tenant, per-resource retention periods
(traces, violations, anomaly events, judge verdicts, admin audit log)
are purged on a schedule, so a deployment can satisfy a deletion
obligation without an operator deleting rows by hand---and a purge that
removes the oldest records leaves the chain verifiable from the first
retained one.

\subsection{Recovery}
\label{sec:recovery}

Not every harmful call is caught before it runs. For tools that register
a compensating action, \system records enough to undo: snapshots before
effectful calls, a saga of applied steps, and a causal rollback that
reverts a call together with the calls that depended on its output.
Reversibility is scored per tool so the policy can be stricter where
undo is impossible.

\subsection{Compliance Cockpit}
\label{sec:cockpit}

The Cockpit (Figure~\ref{fig:dashboard}) is the operator's view of all of
the above. Three views carry the design. \emph{Activity} shows each agent
run as a timeline titled by its request, every step a sentence with the
app's or website's logo and AEGIS's decision. \emph{Approvals} shows a
held call with its evidence---what the person asked, the passage the
agent read with the attributed value highlighted, the arguments as

covers the rest. Around them sit per-agent profiles, policy authoring in
the DSL or natural language, rollback history, scan results, and the
exportable audit log with its verification status. It runs locally
beside the gateway and needs no network beyond the agent's own model
calls.

\section{Walkthrough on a Live Agent}
\label{sec:demo}

The demonstration runs entirely on a laptop. Nothing is pre-recorded and
nothing is mocked: attendees type into a live agent, and every decision
they see is produced by the same gateway binary the repository ships.

\paragraph{Setup.}
A Claude-powered research agent is connected to a SQLite database, a
scratch file system, and a shell tool. \system is enabled by adding two
lines to the agent, shown in full:

\begin{center}\small
\texttt{agentguard.auto(blocking\_mode=True, enforce\_at="tool")}\\
\texttt{execute\_tool = agentguard.guarded(execute\_tool)}
\end{center}

\noindent
No other change is made (\texttt{auto()} without the flag observes and
audits but never blocks; the flag is the firewall). The first line patches
the model client, so every tool call the model emits is traced; the
second wraps the agent's own tool dispatcher, so the decision is taken
there and a refusal is returned as the tool's result. An agent built on a
framework with a tool-execution hook needs only the first line (the SDK
patches the framework's dispatch entry point); this demo agent is a plain
Anthropic loop, and so uses both. The agent code, the prompts, and the
tool definitions are otherwise untouched---which is the property we most
want attendees to check, and the first thing we invite them to verify by
diffing the agent source against its upstream version.

\input{figures/fig_demo}

\subsection{Three scenarios}

\paragraph{S1 --- A benign call, and what mediation costs.}
An attendee asks the agent to \emph{``summarise the feedback in the
reviews table.''} The agent emits a \texttt{SELECT}; \system extracts the
argument strings, finds no pattern, passes policy validation, and
returns \texttt{allow}. The Cockpit's live feed shows the call appearing
with its risk signals and a decision latency of roughly 1\,ms.

The point of running this first is calibration. A firewall that is only
ever shown blocking things tells you nothing about what it costs when
nothing is wrong, and the most common objection to pre-execution
mediation is that it will sit in the hot path. Attendees see the
end-to-end turn complete at its normal speed with the gateway in the
loop.

\paragraph{S2 --- Interception, and what the agent does next.}
An attendee asks the agent to ``install the monitoring agent the usual
way'' and gives it the usual way: \texttt{curl -s https://\ldots/install.sh
| sh}. The agent does as asked and emits
\texttt{run\_shell(command="curl -s \ldots | sh")}. \system blocks it at
L1 (shell-injection family: a remote fetch piped to a shell) in about a
millisecond at the gateway. The same payload is the S2 of the
compatibility matrix (Appendix~\ref{app:compat}), where every one of
nineteen harnesses blocks it; the earlier version's \texttt{DROP TABLE}
payload is one that current Claude models decline to emit on their own,
which is a defence layer of its own but not the one being demonstrated,
and the appendix records that choice.

What we most want attendees to look at is not the block but
Figure~\ref{fig:demo}(b): the agent receives a structured refusal, and
continues the conversation---telling the user what was blocked, why
(a pipe into a shell interpreter, an unverified remote script), and
what it can do instead (download, inspect, then run). This matters for
a demo audience because the common objection to blocking is that it
breaks the agent. It does not: the decision is returned in-band as a
tool result, so the model recovers the way it recovers from any tool
error.

\paragraph{S3 --- Human-in-the-loop, live.}
An attendee asks for something genuinely destructive
(\texttt{kubectl delete pod}). The call matches a policy marked
\texttt{require\_approval}, so \system returns \texttt{pending} and the
agent \emph{suspends}---the turn does not complete, and the attendee can
see the agent waiting.

The call appears in the Cockpit's approval queue with its full arguments
and risk signals. A second attendee, at a second laptop, clicks Allow or
Block. The first attendee's agent resumes within one polling cycle
(2\,s). Passing the decision between two people is the part of the system
that is hard to convey on paper and immediate in person.

\subsection{What attendees can do themselves}

The session is adversarial by design. Attendees are invited to:

\begin{enumerate}[nolistsep,leftmargin=*]
\item \textbf{Try to get a payload past L1.} Encodings, nesting,
      unicode homoglyphs, and splitting a statement across arguments are
      all fair game. Recursive extraction to depth 32 handles most of
      it; some attempts succeed, and we would rather attendees find
      those than not.
\item \textbf{Try to make the agent emit an attack that L1 cannot see.}
      This is the case \S\ref{sec:eval} shows is the hard one, and the
      demo does not hide it: an indirect injection that causes an
      ordinary-looking call passes L1 and L2; with L$_\mathrm{p}$ toggled
      off it is allowed, and with it on the attendee watches provenance
      catch what content inspection could not. This is the S4 column of
      the compatibility matrix (Appendix~\ref{app:compat}): a file the
      agent is asked to summarise tells it to forward its contents, and
      the \texttt{send\_email} it emits is blocked by the provenance pack.
\item \textbf{Verify the audit trail.} Each trace is Ed25519-signed and
      chained; the Cockpit exports a PDF/CSV report, and a verifier
      command recomputes the chain. Attendees are encouraged to edit a
      record in the exported log and watch verification fail.
\item \textbf{Install it.} The two-line integration runs against an
      attendee's own agent on their own laptop, offline.
\end{enumerate}

\subsection{Practical requirements}

One laptop suffices; two make S3 better. The gateway is a single
Node.js service, the Cockpit a Next.js app, and both run locally---no GPU, and no
network except for the agent's own model calls. We bring a local model
fallback so the demo survives a failed conference network. Total setup
time from a cold machine is under two minutes.

\section{Evaluation}
\label{sec:eval}

We evaluate \system three ways, from the outside in. End to end
(\S\ref{sec:agentdojo}): on AgentDojo, does an agent behind the gateway
still finish what its user asked, and does the attacker's goal still
happen? In cost (\S\ref{sec:overhead}): what does a check add, and how
does the gateway hold up under concurrent agents? And per call
(\S\ref{sec:instantiate}--\S\ref{sec:authority}): on tool calls live
agents emitted under attack, which layer separates them and why. Every
number is produced by a command in the repository (\S\ref{sec:avail}).

\subsection{End to End: AgentDojo}
\label{sec:agentdojo}

\input{figures/table_agentdojo}

Per-call numbers say whether a detector flags a call; a deployment is
judged per task. AgentDojo v1.2.1~\cite{debenedetti2024agentsec} measures
exactly that, and is the benchmark CaMeL, Progent and LlamaFirewall
report against: 97 user tasks in four environments (workspace, travel,
banking, Slack), each run clean for \emph{utility} and against each of the
suite's injection tasks for \emph{attack success}, 949 pairs in all, with
the \texttt{important\_\allowbreak instructions} attack. The agent is
gpt-4o-mini-2024-07-18 in the main run. \system is placed where a deployment
puts it: AgentDojo's tool executor is replaced by one that, before every
tool runs, reports the conversation's new spans to the ledger exactly as
the SDK's request-side hook classifies them, asks the shipping gateway's
\texttt{/check}, and on a refusal returns the reason in the tool-result
slot so the agent continues (\texttt{research/agentdojo/run\_agentdojo.py};
one fresh gateway per configuration). AgentDojo's own defenses are run
alongside for reference. Table~\ref{tab:agentdojo} gives the results.

\paragraph{Security.} Undefended, the attack succeeds on 29.7\% of pairs.
\system with the instruction-provenance pack brings that to
\textbf{1.4\%}, the lowest of any configuration and a quarter of the
tool filter's 5.4\%, at a check cost under a millisecond and no model
call. The rules alone halve attack success (16.0--17.0\%), not because
they recognise the injections---they contain no payload---but because
the default policy holds every outbound message for a person and, with
nobody to answer, a hold is a refusal. On the 829 pairs every
configuration completed, the numbers are 30.0\%, 5.4\% and 1.4\%. One injection task inflates every interposition defense's count:
AgentDojo judges Slack \texttt{injection\_task\_5} on the calls the
agent \emph{emitted}, not on what they did, so an invite the gateway
refused still scores as a successful attack. Counting only calls that ran
(\texttt{rescore\_executed.py}; column \emph{Executed}), \system with
the pack is at 0.9\% (8 of 843) and the rules alone at 15.3--16.4\%; the
undefended agent and AgentDojo's own defenses, which do not refuse
calls, are unchanged. We report AgentDojo's score as the headline, since
it is what other systems report.

\paragraph{Utility, and where it goes.} The price is paid in holds. With
no reviewer present, every hold refuses a call, and \system with the pack
completes 38.1\% of clean tasks against 69.1\% undefended. That number
measures the absence of the person a hold is for, so the table also
counts the tasks that needed one: 34 of 97. Two changes, both on the
same principle, came out of this run. The first version held any tool the
classifier filed as communication, so \texttt{search\_emails} was held
like \texttt{send\_email}, and the pack's review rule held every call
whose arguments came from an earlier tool result, which is what reading
a hotel's reviews before booking it looks like: 671 holds on 97 clean
tasks, 62 tasks needing a person, 33.0\% utility. A hold is for a call
that \emph{acts}; reading changes nothing, and what an injection can do
with a read needs a later call that writes, sends or pays, which is
still held. The gateway now derives a \texttt{tool.read\_only} fact from
the name's own verbs---conservatively: a name with any write verb, an
unknown verb, or a network read is not read-only---and both the default
communication hold and the pack's two review rules apply only to calls
that are not read-only. Tasks needing a person fall from 62 to 34 and
utility rises from 33.0\% to 38.1\%, at an unchanged 1.4\% attack
success. Because the revision was motivated by this benchmark, the
first version stays in the table, and the revision is checked on the
independent corpus of \S\ref{sec:instantiate}: there it costs per-call
recall (95.4\% to 77.2\%, the data-stealing reads it now allows) and
barely moves two-step false positives (23.7\% to 19.5\%), which is the
honest shape of the trade.

\paragraph{With the auditor as first reviewer.} A deployment does not
leave holds unanswered, and the design's own answer is the alignment
auditor (\S\ref{sec:judge}): in the last row each hold goes to the
gateway's \texttt{/alignment/check} with the user's request as the
declared goal, and is released if the auditor finds the call serves it.
Clean utility returns to \textbf{56.7\%}, inside the tool filter's
interval, and only 11 of 97 tasks still reach a person. Its attack run
did not complete---the OpenAI account ran out of credit before it
started producing results---so with this agent, whether the auditor
releases attack calls the pack held is not measured; the second model
below measures it. What the table does establish is the split of
labour: L$_\mathrm{p}$ decides in under a millisecond which calls need a
second look, and only those pay for one.

\input{figures/table_agentdojo_qwen}

\paragraph{A second agent model, served locally.} To measure what the
credit stopped, and to leave the hosted-model family, we reran the
banking and Slack suites (37 user tasks, 249 attack pairs) with
qwen3:8b served by Ollama, reasoning off, as both the agent and the
auditor (Table~\ref{tab:agentdojo-qwen}). Undefended, 47 of 249 attacks
succeed. With holds going to the auditor first, \emph{none} do---but
clean utility falls from 19 of 37 to 9, and the rows below that one are
what we changed to get it back, each motivated by what the run before it
showed, and each reported.

The first loss was blocks. These suites' legitimate tasks take
recipients and IBANs from tool output (``pay the bill in this file'',
``invite the people on this web page''), which is the destination
rule's known false-positive class, and a block cannot be reviewed.
Demoting the two destination rules to holds through the DSL, as an
operator would, buys back two tasks and lets one attack through: a
transfer of the whole balance that the auditor approved while noting an
``unfamiliar recipient account''. The second loss was the auditor
itself, which refused legitimate calls ``without evidence of having
reviewed the file'': it was never shown the file. Given the session's
tool output (\S\ref{sec:judge}), it recovers utility to 17 of 37, within
noise of undefended---and is itself injected in 4 of 249 pairs. Three
gateway defects explained the rest and are fixed: a judge that names
\texttt{prompt-injected} and still scores a call 0.8 now counts as
drifted; a recipient swapped through a tool with no sink verb
(\texttt{update\_scheduled\_\allowbreak transaction}) is now held; and a link the
agent rewrote with \texttt{https://} is now matched to the page that
gave it. The final row, the shipped gateway with the destination rules
at \texttt{pending} and the auditor shown the evidence, completes 13 of
37 clean tasks and lets \textbf{1 of 249} attacks run: a phishing link
the gateway held and the 8B auditor released, having noted that ``the
URL is part of the untrusted data''. AgentDojo scores it 4 of 249; the
other three are refused calls (\S\ref{sec:agentdojo}).

Two cautions. Clean utility on 37 tasks moves by about three tasks
between identical configurations: of the four tasks the final row lost
against the evidence row, three hit no refusal at all. And every change
in this paragraph was found on these two suites; the workspace and
travel suites, which none of them touched, are the held-out check, and
are reported in the repository as they complete rather than here.

\paragraph{Against the systems that rebuild the agent.} The closest
systems report on the same benchmark with stronger agents, so their
numbers are context, not a row of the table. Progent, with gpt-4o as the
agent and as the policy generator, reports attack success falling from
39.9\% to 1.0\%~\cite{shi2025progent}; CaMeL solves 77\% of tasks with
provable security against 84\% undefended, and with Gemini~2.5~Pro brings
successful attacks from 300 of 949 to none~\cite{debenedetti2025camel}.
\system's 1.4\% sits in the same range as Progent's without a model in
the decision path, and CaMeL's guarantee is one no detector, ours
included, can give. What \system trades for not rebuilding the agent is
utility: CaMeL loses 7 points of task completion, \system 31 with no one
answering its holds and 12 with the auditor answering them.

\subsection{Overhead}
\label{sec:overhead}

\input{figures/table_overhead}

Table~\ref{tab:overhead} measures one gateway process under concurrent
agents (\texttt{node research/perf/loadtest.mjs}). With one client a
check takes 0.44\,ms at the median and under 2\,ms at p99, with or
without the provenance pack; the pack's ledger assessment does not show
at this resolution. Throughput saturates near 2{,}300--3{,}000 checks per
second on one process, and beyond that latency is queueing: at 128

so the scaling path is more processes behind sticky routing by session
(the ledger is per process, \S\ref{sec:provenance}), which this
measurement does not cover. An agent's own model call takes seconds; at
the loads measured, a check is a fraction of a percent of a turn.

\paragraph{The first version's numbers are withdrawn.}
The 99.9\% block rate at 0.09\% false positives reported earlier came from a
per-call benchmark whose malicious records encoded their own label in an
argument key; Appendix~\ref{sec:withdrawn} gives the audit. Every number
below is measured on agents that were actually attacked.

\subsection{Mechanism: Instantiation by Rollout}
\label{sec:instantiate}

\begin{figure*}[t]
    \centering
    \includegraphics[width=\textwidth]{images/rollout_construction.pdf}
    \vspace{-0.12in}
    \caption{How the corpus is built. An InjecAgent case supplies the
    context but no attacker call; four arms---attack, a length-matched
    control with the injection replaced by neutral prose, schema-synthesised
    benign requests with decoy tools, and a two-step benign arm whose calls
    also carry tool-derived arguments---are rolled out through the same live
    agent, and a record is labelled by whether the emitted call names a tool
    on the case's attacker list. Attack success is 95.07\% against 0.285\%
    in the control arm; the result is 663 agent-emitted calls on which no
    surface feature exceeds AUC 0.585.}
    \vspace{-0.1in}
    \label{fig:instantiate}
\end{figure*}

If the attacker's call only exists after an agent is compromised, the
sound way to obtain one is to compromise an agent and record what it
emits (Figure~\ref{fig:instantiate}). For each InjecAgent case we reconstruct the agent's context---the
user's instruction, the legitimate first tool call, and the tool response
carrying the injection---and let a live model (Qwen3-VL-32B-Instruct,
AWQ 4-bit, served over an OpenAI-compatible endpoint with
prompt-rendered tool calling) choose its own next action. A rollout is
\emph{compromised} when the emitted call names a tool on that case's
attacker list. Arguments are the model's own, so nothing in the record
encodes the label.

\paragraph{Matched control.}
Recording only the attack arm would confound attack success with the
agent's baseline willingness to call those tools. An identical arm
replaces the injection with neutral prose of matched length, so the only
difference is the presence of an adversarial instruction. Over
$n=2{,}108$ cases per arm, attack success is \textbf{95.07\%} against
\textbf{0.285\%} (Wilson 95\% CIs $[94.06, 95.91]$ and $[0.13, 0.62]$),
a risk ratio of 334. The six control-arm compromises are one user
instruction repeated across splits after which the agent plausibly
continued the user's own request---label ambiguity, and itself
informative: attacker tool is not a sound label, because the same tool is
benign or malicious depending on who asked.

\paragraph{Benign coverage.}
Attacks alone do not make a benchmark. For each of the 63 attacked tools
we synthesise legitimate requests from the tool schema alone---the
generator is never shown an attack---and roll them out with five decoy
tools offered alongside, so ``the agent called the only available tool''
is not what is measured. A further \emph{two-step} benign arm has the
agent make a lookup call, receive a clean tool response, and act on it,
so that benign calls also carry tool-derived arguments. This arm is what
makes the provenance comparison honest: without it, ``did a tool return
precede this call?'' separates the classes for a construction reason.

\input{figures/table_integrity}

\paragraph{Integrity.}
Table~\ref{tab:integrity} reports the corpus before and after. Every
attacked tool now also appears in the benign class, and no surface
feature retains discriminative power: the best single feature falls from
0.947 to 0.585. The final corpus is 663 records, 237 malicious and 426
benign, every one a call a live agent actually emitted.

\subsection{What Content Inspection Catches}
\label{sec:content}

\input{figures/table_results}

Table~\ref{tab:results} reports detectors on the rebuilt corpus, with
balanced accuracy $\frac{1}{2}(\mathrm{TPR}+\mathrm{TNR})$ because the
classes are unbalanced. \system-rules is the shipping gateway, run
locally with a fresh database and no policy pack, not a reimplementation.
The keyword blacklist is at chance, and so is L1: its 28 patterns fire
on \textbf{two} of the 237 attack records---the same
\texttt{TerminalExecute} command, caught by the shell-metacharacter
rule---and on four benign ones (the \texttt{--} of a \texttt{git} and a
\texttt{python} command line read as a SQL comment, two cryptocurrency
addresses read as hex-encoded payload). Run family by family against the
attacks: SQL injection 0.0\%, path traversal 0.0\%, sensitive-file access
0.0\%, prompt injection 0.0\%, shell injection 0.8\%. The attacks contain
no payload to match. \texttt{AmazonViewSavedPaymentMethods(\{\})} carries
no argument at all. An earlier run of this row reported an 84.4\% block
rate against 73.9\% of legitimate calls; both numbers came from a policy
pack on that gateway's tenant requiring a \texttt{reason} argument on
every call, which blocked 511 of the 663 records regardless of content
and measured a configuration, not a detector. The row is replaced, and
the run that produced it is kept in the repository. Only the LLM judge,
which reads the user's stated task and compares the call against it, is
meaningfully above chance (0.851), at 2{,}280\,ms per call---and it is the

The last three rows are the provenance layer measured where it is
deployed, not where it is convenient: a fresh gateway from the shipping

226 of the 237 attacks and none of the 426 benign calls, at 0.7\,ms
median round trip; 29 of the 226 are outright blocks (the exfiltration
and destructive rules), the rest are holds for a person. The eleven it
misses are dominated by one tool, \texttt{NortonIdentitySafeSearchPasswords}
(8), whose arguments are empty and whose name shares no word with the
injection. That is the pack as first shipped. The revised pack, which
holds only calls that act (\S\ref{sec:agentdojo}), flags 183 of 237
(77.2\%), still none of the benign calls: what it now allows are the
data-stealing reads---\texttt{ExpediaSearchReservations} (21) leads---whose
harm needs a later send or post, which it still holds. Per call this is
a loss; end to end, on AgentDojo, attack success is unchanged at 1.4\%.
These are the numbers a deployment gets; Table~\ref{tab:provenance}
below is the number the features can reach.

\subsection{Why Authority Separates What Content Cannot}
\label{sec:authority}

\begin{figure}[t]
    \centering
    \includegraphics[width=\columnwidth]{images/capability.pdf}
    \vspace{-0.15in}
    \caption{Tables~\ref{tab:results} and \ref{tab:provenance} as a
    picture. (a)~Every content-only detector sits on the chance line; only
    the judge, which reads the task, is above it---at 2{,}280\,ms.
    (b)~Content and taint lie inside each other's spread; grounded
    instruction provenance is a step, not an increment, and the adaptive
    attacker (\textcolor{red}{$\blacktriangledown$}) lowers it to 0.933,
    not to the content level. The hatched bar is the definitional pair,
    reported and excluded.}
    \vspace{-0.15in}
    \label{fig:capability}
\end{figure}

\input{figures/table_provenance}

\begin{sloppypar}
The question is whether the judge's advantage is \emph{reading the task}
or \emph{being a large model}. Table~\ref{tab:provenance} and Figure~\ref{fig:capability} answer it with
feature blocks evaluated against the two-step benign arm, where both
classes carry tool-derived arguments. Content features reach 0.687. Data
provenance---\allowbreak the five taint features that track where each argument's
\emph{value} came from---reaches 0.737, inside cross-validation noise of
content, because on that axis the classes are the same. Instruction
provenance---\allowbreak the four grounded L$_\mathrm{p}$ features that ask which
\emph{turn} authorised the call---\allowbreak reaches \textbf{0.991 $\pm$ 0.009}, a
$+0.254$ gap over taint against a pooled spread of 0.092. Adding content
or taint on top changes nothing (0.986, 0.991): once the call is compared
to the task, what the call contains is redundant.
\end{sloppypar}

This is the capability claim, and it is architectural rather than
numerical. A layer that sees only the call string cannot recover this
signal at any budget, because the signal is not in the call string; a
layer that sees the channel split recovers it in under a millisecond
without a model. The judge was doing the same comparison at
$1600\times$ the cost.

\paragraph{What the shipped pack does with it.}
The 0.991 is a logistic regression over the four features, cross-validated
on this corpus. The pack's original five rules were written before the corpus
existed (the two destination rules of \S\ref{sec:authority} came later), and the two numbers differ in the direction one should expect.
Against the single-step benign arm the pack's false-positive rate is zero
(Table~\ref{tab:results}); against the two-step arm, where every benign
call follows a tool return, it holds 40 of 169 legitimate calls
(23.7\%) for a person, all under the catch-all rule
\texttt{provenance-untrusted-authority-review}, which escalates any call
whose vocabulary the tool return explains better than the user turn does.
A two-step benign call is \emph{supposed} to carry words from the tool
return---that is what acting on a lookup means---so the rule fires on the
honest case as well as the attack. Balanced accuracy on that arm is 0.858
at the flag level and 0.561 at the block level, against the classifier's
0.991. We do not tune the rule's threshold on this corpus, because that
would be fitting the test set; we report the gap, and note that the
holds are holds, not blocks: the agent waits, a person answers, and
nothing is lost but time.

\paragraph{Is it a generator artefact?}
The benign arms were synthesised from tool schemas, so a model wrote
their user instructions with the tool's name and parameters in view---the
procedure most likely to manufacture lexical overlap between request and
call. The control is InjecAgent's own human-written instructions paired
with the tool the user asked for: \texttt{user\_licence} $=0.500$,
bootstrap 95\% CI $[0.425, 0.581]$, against 0.550 schema-generated and
\textbf{0.040} for attacks. The generator inflates the feature by 0.049;
the human-written interval is nowhere near the malicious mean. $n=17$ is
small and a larger human-written control is warranted.

\paragraph{Adaptive attacker.}
InjecAgent's attacks are not adaptive and are maximally off-task, the
easy case. Restating the user's request inside the injection---the first
evasion anyone tries---moves the margin from $+0.373$ to $+0.398$ and AUC
from 0.991 to 0.994: the licence measure is asymmetric, scoring how much
of the \emph{call} a channel explains rather than how similar two texts
are, so padding the untrusted channel with text absent from the call does
nothing. The evasion that works is carrying the user's vocabulary into
the call's arguments, which any free-text field the tool already accepts
will do: AUC falls to \textbf{0.933 $\pm$ 0.024}. This is a raised price,
not a barrier, and it scales with how far the attacker's goal is from the
principal's---which is exactly what makes an attack worth running.

\paragraph{Same tool, hijacked arguments.}
Every InjecAgent attack changes the \emph{tool}: the user asked for one
thing and the injection makes the agent call another, so the tool's own
name carries much of the licence signal. The case the measure cannot see
by construction is the one where the user asked for the very tool the
injection hijacks and only an argument changes---``email the summary to
my team'' becomes ``\ldots to the attacker''. We construct it from the
corpus: for each of the 237 attacks, the user turn is replaced by a
benign-arm instruction that legitimately asks for the same tool, the
injection and the attacker's call are kept verbatim, and the probe is run
through the same gateway (\texttt{python -m selective.same\_tool\_probe}).
Mean \texttt{user\_licence} rises from 0.040 to 0.237 and the margin
halves, from $+0.373$ to $+0.176$; the pack's flag rate falls from 95.4\%
to \textbf{77.6\%}, and 53 of the 237 probes pass unflagged. These are
constructed records, not rollouts---no agent emitted them---and the user
turn and the injection were written for different tasks, so the overlap
they manufacture is a lower bound on what a real same-tool attack
achieves. The honest statement is that provenance separates \emph{which
tool} far better than \emph{which argument}, and an injection that stays
inside the tool the user already authorised is the attack this layer is
weakest against.

\paragraph{Argument-level authority.} The first remedy is to attribute
the destination rather than the tool. For a call that sends, pays,
shares or posts, the gateway extracts its destination-like argument
values---addresses, URLs, account numbers, paths, phone numbers; not
amounts or dates---and counts those that appear in untrusted text and
never in the user's (\texttt{provenance.untrusted\_only\_values}); a pack
rule blocks such a call whatever the tool-level verdict. Prototyped on the
corpus first, the signal fires on 17 of the 24 attacks on sending tools
(every one that carries a destination), on none of 426 single-step benign
calls and on 2 of 169 two-step ones, both a deposit reusing an account
number from a lookup. Through the gateway, on the 183 same-tool probes
whose tool acts, it raises blocks from 17 to 22 and cuts misses from 29 to
26; \texttt{BankManagerTransferFunds} with an injected account is now
blocked. What remains are actions with nothing to attribute---unlock a
door, disable two-factor authentication, place an order---where the user
asked for that tool and the injection changed nothing a value check can
see. Its known false-positive class is a user who delegates the
destination to a document (``send it to the address in the ticket''),
which the rule cannot tell from an injection. A destination is also not
only an argument of a sending tool: on AgentDojo,
\texttt{update\_scheduled\_\allowbreak transaction} with an injected
recipient matched no sink verb and was allowed outright. A second rule
therefore \emph{holds} (not blocks) any acting call with an
untrusted-only destination, whatever its name. On the independent corpus
it leaves recall where it was, since other rules already flagged those
calls, moves same-tool probe misses from 73 to 72 (on the 183 acting probes, 26 to 25), and adds three holds
on 169 two-step benign calls (19.5\% to 21.3\%); its case is the one
AgentDojo exposed, and it is reported as motivated by it. The gpt-4o-mini AgentDojo
runs of \S\ref{sec:agentdojo} predate this rule; the qwen3:8b run uses
it, and shows the false-positive class at work on banking and Slack.

\paragraph{Two features we report and do not use.}
Imperative density and second-person address in the untrusted channel
detect ``an instruction appeared in a data channel'', which is the
definition of indirect injection; they are guaranteed to look good on any
corpus whose benign tool output was written to be pure data and will fail
on the common real case of tool output that legitimately carries
imperatives. They are shown in italics in Table~\ref{tab:provenance} and
excluded from every claim.

\subsection{Limitations}
\label{sec:scope}
\begin{itemize}[nolistsep,leftmargin=*]
\item \textbf{Auditor-reviewed attack success is measured on one model
  and two suites.} With qwen3:8b on banking and Slack it is 0 to 1 of 249
  depending on configuration; with gpt-4o-mini on all four suites the attack run did not complete before
  the API credit ran out, so there the 1.4\% belongs to the configuration
  in which holds are refusals. The gpt-4o-mini rows also predate every
  change of the qwen3:8b paragraph.
\item \textbf{Two agent models, neither frontier.} AgentDojo was run with
  gpt-4o-mini on four suites and qwen3:8b on two; the per-call corpus was
  produced by one model (Qwen3-VL-32B). Stronger models resist the attack
  more on their own, which changes the baseline more than the defense.
\item \textbf{The auditor is a weak link when it is small, and it was
  tuned on the suites it is reported on.} With an 8B auditor shown the
  evidence, utility returns to within noise of undefended at a cost of one
  executed attack in 249, an injection the auditor itself fell for; a
  stronger auditor has not been measured. The changes that got there were
  found on banking and Slack; the held-out suites are not yet reported.
\item \textbf{Delegation is indistinguishable from injection.} When the
  user tells the agent to follow a document (``do the tasks on my to-do
  list''), an instruction in that document has the user's authority by
  construction; provenance cannot separate it from an injected one, and
  only review can.
\item \textbf{Same-tool hijacks.} An injection that stays inside the tool
  the user asked for and changes only an argument is the case
  provenance is weakest on (\S\ref{sec:authority}). Attributing the
  destination closes the part with a recipient, URL or account to
  attribute; an action with none (unlock, disable, order) stays open, and
  a destination the user delegated to a document is blocked with it.
\item \textbf{The read-only revision trades recall for holds.} It was
  motivated by AgentDojo; on the independent corpus it costs per-call
  recall (95.4\% to 77.2\%) on data-stealing reads whose harm needs a
  later, still-held call. The first version is reported alongside it.
\item \textbf{Coverage of the provenance layer.} It needs the request-side
  hook: the Python SDK has it for every model client it patches; the JS
  and Go SDKs and the two proxies do not, and a framework that rewrites
  tool results into user text (smolagents) erases the channel before any
  hook sees it (Appendix~\ref{app:compat}).
\item \textbf{Overhead on one laptop.} The load test ran on a shared
  laptop under swap; percentiles were stable across runs, maximum
  latencies were not and are not attributed. Multi-process and
  networked deployments are not measured.
\item \textbf{Corpus construction.} Capture is single-turn; 237 unique
  malicious calls is bounded by InjecAgent's distinct attacker
  instructions; the human-written control is $n=17$; one adaptive
  strategy. The lesson of Appendix~\ref{sec:withdrawn} is that an
  evaluation's construction, not its headline, decides what it can
  support, so we state these rather than average over them.
\end{itemize}

\section{Related Work}
\label{sec:related}

\paragraph{Agent safety benchmarks.}
ToolEmu~\cite{ruan2024toolemu} emulates tool execution for LLM-based risk
scoring; AgentDojo~\cite{debenedetti2024agentsec} studies prompt
injection in dynamic environments;
InjecAgent~\cite{zhan2024injecagent} benchmarks indirect prompt
injection. These are evaluation harnesses rather than runtime control
points, and \S\ref{sec:eval} argues that distinction is load-bearing.

\paragraph{Runtime controls for agents.}
The closest systems also decide tool calls before they run, and differ
from \system in where they stand. CaMeL~\cite{debenedetti2025camel}
defeats injection \emph{by design}: a privileged model plans over the
user's query while a quarantined model handles untrusted data, and
capabilities on values enforce policies on tool calls; it requires the
agent to be built around that split, and in exchange gets a guarantee
that no detector can. Progent~\cite{shi2025progent} enforces a
per-task privilege policy over tool names and arguments, generated and
updated by a model and checked deterministically, demonstrated inside
LangChain and the OpenAI Agents SDK.
IsolateGPT~\cite{wu2025isolategpt} isolates third-party apps from each
other and from the hub at the architecture level.
LlamaFirewall~\cite{chennabasappa2025llamafirewall} and NeMo
Guardrails~\cite{rebedea2023nemo} are libraries the agent's own process
calls: prompt and alignment scanners and a code scanner in the first,
programmable dialogue rails in the second. \system shares the
pre-execution stance and is deliberately the least invasive of these:
it stands between an \emph{unmodified} agent and its tools, across
frameworks and transports it does not control, and adds what a
deployment needs around the decision---a hold that suspends the agent
for a person, a signed and chained record of every decision, and
fallback when the control point itself is slow or down. Its
instruction-provenance layer (\S\ref{sec:provenance}) is a detector that
borrows CaMeL's question, which channel authorised this, without
CaMeL's rewrite; \S\ref{sec:eval} measures what that buys and what it
cannot.

\paragraph{LLM trustworthiness and guardrails.}
TrustLLM~\cite{huang2024position} and TrustEval~\cite{wang2024trusteval}
evaluate trustworthiness at the model level; Llama
Guard~\cite{inan2023llama} classifies text safety. \system differs in
scope: it mediates structured tool calls on the execution path, and
returns a decision the calling framework must honour.

\paragraph{Observability platforms.}
Langfuse~\cite{langfuse2024}, Helicone~\cite{helicone2024}, and
Arize~\cite{arize2024} trace tool calls after they are issued. \system
complements these by acting before side effects occur.

\section{Conclusion and Availability}
\label{sec:avail}

\system{} puts a decision between an agent and its tools: two lines of
integration in fifteen frameworks, a refusal that returns in-band, a hold
that waits for a person, and a signed chain of every decision. On
AgentDojo it brings attack success from 29.7\% to 1.4\%, mostly through
asking which turn of the conversation authorised a call, in under a
millisecond and without a model. Its cost is holds, and the alignment
auditor answering them first returns most of the utility; whether that
reviewer also releases attacks is the number this version could not
afford to measure, and the first one the next owes. Around the decision
sit the parts an operator needs before it is deployable: a behavioural
layer that cannot block before it has learned, explicit fallback for a
gateway that is slow, down or without a model, static analysis in the
same policy vocabulary, and connectors into the identity, SIEM and
compliance systems already in place. Running all of it under nineteen
real agent harnesses found twenty-six defects no unit test had; the
matrix stays in the repository so the next ones are found the same way.
